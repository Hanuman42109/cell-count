# Loblaw Bio — Immune Cell Population Analysis

Analysis pipeline and interactive dashboard for cell count data from Bob
Loblaw's clinical trial, evaluating how the drug candidate **miraclib**
affects immune cell populations in melanoma patients.

## Quick start (GitHub Codespaces)

```bash
make setup      # installs dependencies from requirements.txt
make pipeline   # builds cell_counts.db and writes results to outputs/
make dashboard  # launches the Streamlit dashboard
```

`make dashboard` starts Streamlit on port 8501. In Codespaces, a popup will
offer to forward the port — open it (or use the "Ports" tab) to view the
dashboard in your browser.

### Deploying to Streamlit Community Cloud (for a public link)

`dashboard.py` builds `cell_counts.db` itself on first run if it doesn't
already exist (see `require_db()`), so it works on Streamlit Cloud without
needing `make pipeline` to run first.

1. Push this repo to GitHub (public, or private with Streamlit Cloud
   granted access).
2. Go to https://share.streamlit.io and sign in with GitHub.
3. Click **"New app"**, pick this repo/branch, and set the main file path
   to `dashboard.py`.
4. Click **Deploy**. The first load takes a bit longer while it builds the
   database from `cell-count.csv`; after that it's cached.
5. Copy the resulting `https://<app-name>.streamlit.app` URL into the
   "Dashboard link" line above.

## Repository structure

```
.
├── load_data.py       # Part 1: builds cell_counts.db schema and loads the CSV
├── analysis.py         # Parts 2-4: all SQL queries + stats, reused by both
│                        #            run_pipeline.py and dashboard.py
├── run_pipeline.py     # Runs analysis.py end-to-end, writes static CSVs/
│                        #   plot to outputs/ (useful for grading/review
│                        #   without needing the dashboard running)
├── dashboard.py         # Streamlit app: interactive version of Parts 2-4
├── cell-count.csv       # Input data (provided)
├── cell_counts.db       # Generated by load_data.py
├── outputs/             # Generated by run_pipeline.py
├── requirements.txt
├── Makefile
└── README.md
```

**Design rationale:** `analysis.py` contains no I/O side effects beyond
reading from the database — it's a library of pure functions
(`get_frequency_table`, `compute_response_statistics`,
`get_baseline_subset`, etc.). Both `run_pipeline.py` (batch/CLI output) and
`dashboard.py` (interactive UI) import from it, so the analysis logic is
written and tested in exactly one place, and the dashboard can never drift
out of sync with the "official" pipeline output. `load_data.py` is kept
separate and self-contained per the assignment's explicit requirement that
it be independently runnable with no arguments.

## Database schema (Part 1)

The raw CSV is wide and denormalized: subject-level attributes (project,
condition, age, sex, treatment, response) are repeated on every sample row,
and each of the five cell populations is hard-coded as its own column. I
normalized this into five tables:

```
projects (project_id PK, name)
        │
        ▼
subjects (subject_id PK, project_id FK, condition, age, sex, treatment, response)
        │
        ▼
samples (sample_id PK, subject_id FK, sample_type, time_from_treatment_start)
        │
        ▼
cell_counts (sample_id FK, population_id FK, count)   -- composite PK
        ▲
        │
populations (population_id PK, name)
```

- **projects / subjects / samples** reflect the real one-to-many hierarchy
  in the data: a project has many subjects, a subject contributes multiple
  samples over time. I verified in the source data that project, condition,
  age, sex, treatment, and response are constant per subject (never vary
  across a subject's samples), so they belong on `subjects`, not repeated
  on every sample row — this removes redundancy and the risk of a subject's
  metadata becoming inconsistent across rows.
- **populations** is a lookup table rather than fixed columns
  (`b_cell`, `cd8_t_cell`, ...). This means adding a sixth population (e.g.
  a new marker panel) is a data insert, not a schema migration or a change
  to every query that currently lists five columns by name.
- **cell_counts** is the fact table: one row per (sample, population),
  which is the "long" / tidy form of the CSV. This is what makes the SQL
  in `analysis.py` simple — e.g. computing each sample's total count and
  per-population percentage is a single query using a window function
  (`SUM(count) OVER (PARTITION BY sample_id)`), rather than hard-coding
  five column names into an expression.
- Indexes on the foreign keys (`subject_id`, `sample_id`, `population_id`)
  keep the joins used throughout Parts 2-4 fast.

This is a standard star-like design: `subjects`, `samples`, and
`populations` are dimension tables; `cell_counts` is the fact table.

**Scaling to hundreds of projects, thousands of samples, and more analytics:**

- The row counts in the dimension tables grow linearly and cheaply —
  `projects` and `populations` stay small regardless of trial size, and
  `subjects`/`samples` scale to the tens/hundreds of thousands without
  needing schema changes, given the indexes already in place.
- The long/tidy `cell_counts` table means new cell populations, new
  metadata fields on subjects, or new sample-level attributes can be added
  without rewriting existing queries — only `subjects`/`samples` gain a
  nullable column, or `populations` gains a row.
- For hundreds of projects and heavier analytical workloads, I'd migrate
  from SQLite to a server-based engine (Postgres) so multiple analysts and
  the dashboard can query concurrently, and I'd add:
  - a `sample_metadata` or `assay_batch` table if additional per-sample
    experimental metadata (e.g., batch, instrument, QC flags) is needed,
    rather than continuing to widen `samples`;
  - materialized views (or a small nightly ETL job) for the Part 2
    frequency table, since it's recomputed identically for every
    downstream analysis and is the highest-cardinality query;
  - partitioning `cell_counts` by project or time if it grows into the
    hundreds of millions of rows.
- The overall shape (dimensions + a tidy fact table) doesn't change — it's
  the same pattern used in most clinical/genomics data warehouses, which
  is why I chose it here rather than a bespoke one-off schema.

## Part 2 — Frequency table

For each sample, total cell count is the sum of all five population
counts; each population's relative frequency is `100 * count / total`.
Implemented as a single SQL query using a window function
(`get_frequency_table` in `analysis.py`), exposed in the dashboard's first
tab and written to `outputs/part2_frequency_table.csv`.

## Part 3 — Responder vs non-responder analysis

Restricted to **melanoma, miraclib-treated, PBMC** samples with a
non-null response label (per the assignment's "please only include PBMC
samples" instruction).

- **Visualization:** boxplot of relative frequency per population, split
  by response (dashboard tab 3, and `outputs/part3_boxplot.png`).
- **Statistics:** a **Mann-Whitney U test** per population, comparing
  responders' vs non-responders' relative frequencies, with a
  rank-biserial effect size. I chose Mann-Whitney over a t-test because
  once you filter down to melanoma/miraclib/PBMC, group sizes per subject
  are modest and relative-frequency data is often skewed/bounded — a
  non-parametric, rank-based test doesn't require a normality assumption
  and is standard practice for this kind of immunology comparison.
- **Result:** at the sample level (n=993 responder samples, n=975
  non-responder samples, from 656 unique subjects), **CD4+ T cells** show
  a statistically significant difference (p ≈ 0.013, two-sided
  Mann-Whitney U), with responders trending slightly higher. No other
  population reaches significance at p < 0.05 in this dataset. Given the
  modest effect size, this is best framed to Yah as a hypothesis-generating
  signal worth validating in a larger or independent cohort, not a
  confirmed biomarker.

## Part 4 — Baseline subset analysis

1. Filtered to melanoma + PBMC + miraclib samples at
   `time_from_treatment_start = 0` (dashboard tab 4).
2. Breakdown of that subset by project, responder/non-responder subject
   counts, and male/female subject counts (dashboard tab 4, also written
   to `outputs/part4_*.csv`).
3. **Considering melanoma males of all sample and treatment types**, the
   average B cell count for responders at time = 0 is **10206.15** (see
   `outputs/part4_avg_bcell_male_responders_baseline.txt`, computed by
   `get_avg_bcell_male_melanoma_responders_baseline` in `analysis.py`).
   Note this question intentionally does *not* restrict to miraclib or
   PBMC — it's a broader query across all treatments and sample types for
   melanoma male responders at baseline.

## Reproducing results outside the dashboard

```bash
python load_data.py       # build cell_counts.db
python run_pipeline.py    # write outputs/*.csv and outputs/part3_boxplot.png
```

`python analysis.py` on its own also prints all four parts' key outputs
to the terminal, useful for a quick sanity check.
